# The `@claude` agent-mode harness

`.github/workflows/claude.yml` runs `anthropics/claude-code-action@v1` in
**agent mode** rather than the packaged `@claude` mention flow. Agent mode is
selected by one thing and nothing else: supplying a `prompt:` input. Everything
the packaged flow used to do — build the prompt, gate the trigger, post a
tracking comment, hand back a "Create a PR" compare link, append its own footer
to pull request bodies — is then this repository's job.

That is the point. What this repository publishes should be written by this
repository. It is also a liability: the parts the action stopped doing include
two it was doing for safety, so those are re-implemented here, deliberately and
with tests.

- Workflow: [`.github/workflows-pending/claude.yml`](../.github/workflows-pending/claude.yml)
  — pending activation, see [Landing changes](#landing-changes-to-this-harness)
- Preparation: `.github/scripts/claude-agent-harness.sh`
- Publishing guards: `.github/scripts/claude-agent-guard.sh`
- Tests: `.github/scripts/test-claude-agent-harness.sh` (`task test:agent-harness`)

## What the two modes actually differ on

Read from the action source at `v1`, not from its documentation:

|                  | tag mode                                                                                                 | agent mode                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Selected by      | `@claude` in the event body                                                                              | a non-empty `prompt:` input                                            |
| Prompt           | generated by `src/create-prompt/index.ts`                                                                | your `prompt:`, written verbatim                                       |
| Tracking comment | created, then edited with a job link, a branch link and a compare URL                                    | none — `prepareAgentMode` returns `commentId: undefined`               |
| PR body footer   | `This PR addresses #N\n\nGenerated with [Claude Code](…)` (`src/entrypoints/update-comment-link.ts:161`) | never reached; `updateCommentLink` is guarded on the comment id        |
| Permission flags | hardcodes `--permission-mode acceptEdits --allowedTools …`                                               | injects nothing; `claude_args` is the whole story                      |
| MCP servers      | comment + CI servers always                                                                              | only those named in `--allowedTools` (`src/mcp/install-mcp-server.ts`) |
| Branch           | created and checked out                                                                                  | **not created, not checked out**                                       |
| Actor check      | write permission + human actor                                                                           | write permission + human actor                                         |

The last two rows are the ones that cost something.

## The trust boundary is the workflow condition

Agent mode's own gating is `checkHumanActor` (excludes bots) plus
`checkWritePermissions` (passes for any collaborator). This job holds
`contents: write`, `id-token: write`, every repository secret, the OIDC minting
credentials the signing shim needs, and `--permission-mode bypassPermissions`.
"Any collaborator" is not the right audience for that, and neither is "anyone
who can comment".

So the gate is the job's `if:`, and it is owner-only:

```yaml
if: >-
  github.actor == github.repository_owner &&
  github.event.sender.type == 'User' && ( … per-event trigger match … )
```

Each event is matched against its own field. A single `contains()` over
`github.event.issue.body` would fire on _every_ comment made on an issue whose
body happens to mention `@claude`.

The same owner test is repeated inside `claude-agent-harness.sh`. That is not
belt-and-braces for its own sake: GitHub withholds the `workflows` permission
from App installation tokens, so this repository's own automation cannot edit
`claude.yml`. The workflow half of any change to this harness lands by a
different route than the script half, and a gate that exists only in the file
that is hardest to change is a gate nobody notices has been widened.

## Ref selection is explicit, and refuses rather than guesses

`prepareAgentMode` sets `branchInfo.currentBranch` to the base branch and does
not touch the working tree. Left alone, a session triggered from an issue would
edit whatever `actions/checkout` left checked out — `master`.

`claude-agent-harness.sh` decides instead:

| Trigger                                                                                 | Ref                                                                                                                                                                         |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `issues`, or `issue_comment` on an issue                                                | fresh branch `issue-<n>-<slug>` cut from the default branch; an existing branch of that name is _continued_, so a second request on one issue converges on one pull request |
| `issue_comment` on a pull request, `pull_request_review`, `pull_request_review_comment` | that pull request's existing head branch                                                                                                                                    |

and refuses, non-zero and annotated, when the context is not one it can safely
write:

- the actor is not the repository owner;
- the event is not one of the four it normalizes;
- the request carries no trigger phrase (the body, or the title as well for a
  new issue — the same fields the workflow condition reads, because a harness
  that refuses what the condition admitted is a job that fails itself);
- the pull request head is on a fork (`GITHUB_TOKEN` is read-only there anyway,
  so the alternative is discovering it at `git push`, after the work);
- the pull request is closed or merged;
- the pull request head _is_ the default branch;
- the head ref is not a name worth handing to `git`.

The branch name comes from the issue title rather than from the action's
`claude/issue-N-<timestamp>` default, because CLAUDE.md asks for branch names
that describe the change rather than its author. The session may rename it once,
before the first push, to a conventional `feat/` or `fix/` name.

## The request body is data, never a command line

The triggering comment never passes through a YAML expression, a step output or
a shell interpolation. `claude-agent-harness.sh` writes it to a file and the
prompt tells Claude to read that file. This is the whole mitigation for GitHub
Actions script injection: text that is only ever data cannot become part of a
command.

Inside the file it is fenced, and the fence is grown until the body cannot close
it, so a request containing a code block cannot break out of the quoted region
into the surrounding instructions. It is labelled `UNTRUSTED INPUT` with an
explicit statement of what it is not allowed to do.

## Which token opens the pull request

GitHub raises **no workflow events** for actions taken with a workflow's own
`GITHUB_TOKEN`. A pull request opened with it arrives with zero checks: nothing
for branch protection to require, and no fix short of closing and reopening it
by hand.

`claude-code-action` avoids this without being asked to. `src/entrypoints/run.ts`
exchanges the job's OIDC token for a **Claude App installation token** and sets
both `GITHUB_TOKEN` and `GH_TOKEN` to it before spawning the CLI;
`base-action/src/parse-sdk-options.ts` copies the whole environment into the
session, deleting only the two `ACTIONS_ID_TOKEN_REQUEST_*` variables. So `gh`
inside the session authenticates as a _different app identity_ than the
workflow, and pull requests it opens do trigger CI.

That is a property of the action's internals, not of anything configured here,
and it has exactly one configuration that breaks it: re-exporting
`github.token` as `GH_TOKEN` on the action step — which is what this workflow
used to do, harmlessly, because `run.ts` overwrote it. It is now removed, and
the property is checked per run instead of assumed:

```console
$ bash .github/scripts/claude-agent-guard.sh pr-token
ok: session token is not the workflow GITHUB_TOKEN; a pull request opened now will trigger normal CI
```

The check is a SHA-256 comparison. The harness step is the only step handed
`github.token`; it writes the digest — never the token — to
`$RUNNER_TEMP/claude-harness/workflow-token.sha256`, and the guard hashes the
session's own `GH_TOKEN` and refuses if the two match. Neither token is ever
printed. The prompt requires `pr-token` to pass before `gh pr create`.

## Attribution

Pull request titles, pull request bodies, commit messages and comments are the
maintainer's own words. Agent mode already removes the two places the action
injected its own branding, but the model has read a great deal of text that ends
that way, so "please do not" is backed by a check:

```console
$ bash .github/scripts/claude-agent-guard.sh attribution /tmp/pr-body.md
$ bash .github/scripts/claude-agent-guard.sh commits origin/master
```

Refused: `Generated with Claude Code`, `Created with Claude`,
`Co-Authored-By: Claude`, `claude.ai/code` and session links, robot-emoji
`Generated` sign-offs, `powered/assisted/written by Claude`, `generated by
Claude/Anthropic`, `via Claude Code Action`.

Allowed, deliberately: a human `Co-authored-by:` trailer, and naming
`claude-code-action` in prose when the change is about it. A rule that forbade
those would be worked around rather than followed.

The check is blunt on purpose. It matches the banned strings wherever they
appear, including inside quotation marks — so prose that needs to _talk about_
the footer has to describe it rather than reproduce it. That cost is real (the
commit introducing this harness had to be reworded) and it is the right trade:
a rule that tried to tell a genuine footer from a quoted one would be a rule
with a bypass in it, and the remedy here is one sentence of rewriting.

## What was kept

The rewrite touches the harness, not the machinery around it. Still in place:

- `.github/actions/setup-claude-signing`, so commits made in the run are
  GPG-signed by this service over an OIDC-authenticated `/sign` call, and the
  preflight still fails closed;
- `GIT_AUTHOR_*` / `GIT_COMMITTER_*` from repository variables, which outrank
  the bot identity the action writes into `git config`;
- mise, dprint, bun and `runner install`;
- the Cloudflare MCP servers from `.mcp.json`;
- `--permission-mode bypassPermissions` and broad tool access, which are
  deliberate: the owner gate is the boundary, not the tool allowlist.

## Landing changes to this harness

`.github/workflows/claude.yml` cannot be pushed by this repository's own
automation. GitHub withholds the `workflows` permission from App installation
tokens, so any push touching `.github/workflows/` is rejected outright — and the
rejection kills the whole push rather than just that one file.

The agent-mode workflow therefore ships in `.github/workflows-pending/`, the
same convention [`claude-dependabot-fix.yml`](../.github/workflows-pending/claude-dependabot-fix.yml)
uses. It **replaces** the tag-mode workflow still live at
`.github/workflows/claude.yml`. Activate it with one command:

```bash
git mv -f .github/workflows-pending/claude.yml .github/workflows/claude.yml
```

Nothing else changes. `task test:agent-harness` resolves the pending path first
and the live path after, so its assertions guard the file both before and after
the move; `task lint:actions` runs actionlint over both directories. Until the
move happens the suite prints:

```console
note: the agent-mode workflow is still pending activation (git mv -f …)
note: .github/workflows/claude.yml is still the tag-mode harness
```

The workflow missing from _both_ directories is a hard failure, not a skip.
